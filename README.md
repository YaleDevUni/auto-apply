# autoapply v2

채용공고 수집 → 필터 → **지원가능성 판정**. 사람이 UI에서 훑는 게 아니라,
자동화 에이전트가 DB를 읽고 지원 가능한 것만 골라 지원하는 것을 전제로 만들었다.

```bash
python cli.py scrape      # 수집 + 판정
python cli.py targets     # 에이전트가 지원할 목록 (JSON)
python cli.py blocked     # 왜 아무것도 지원 안 했는지
python cli.py status      # 한 줄 요약
```

## v1과 무엇이 다른가

v1은 사람이 보는 칸반(`미확인 / 관심 / 작성중 / 지원완료`)이 중심이었다. 무인 운영에는
그 상태기계가 필요 없다. 대신 두 가지를 새로 세웠다.

### 1. 판정 축을 둘로 갈랐다

| 축 | 질문 | 테이블 |
|---|---|---|
| 적합도 | 이 공고가 나한테 맞나 | `screening` (v1 로직 그대로 — 검증됨) |
| 지원가능성 | 이걸 자동으로 지원할 수 있나 | `applicability` (신규) |

둘은 직교한다. 실측에서 132점짜리(러쉬에잇 백엔드)가 `NO_RECIPE` 하나 때문에 막혔고,
반대로 점수는 낮은데 폼이 단순한 공고도 있다. 하나의 점수로 뭉개면 에이전트는
**"왜 지원 안 했는지"를 설명할 수 없다.**

### 2. 중복지원을 DB가 막는다

`apply_ledger.canonical_key`에 UNIQUE를 걸었다. 지원을 *시도하기 전에* 선점 행을
넣으므로, 지원 도중 프로세스가 죽어도 다음 실행이 같은 자리를 다시 건드리지 않는다.

실측에서 바로 값을 했다 — 원티드가 같은 자리(바카티오 `Backend Engineer`)를
`id=280`, `id=281`로 두 번 올려놨고, 2차 선점이 차단됐다.

```
claim(280) → ledger 1     선점 성공
claim(281) → None         같은 자리, 차단됨
```

방어를 코드가 아니라 스키마에 둔 이유: 사람이 안 보는 시스템에서
"죽었다 살아나서 또 지원"은 반드시 일어나고, 그때 사과할 사람이 없다.

### 3. 지원 속도에 상한을 걸었다

UNIQUE 제약은 **"같은 자리에 두 번"만** 막는다. "서로 다른 200개 자리에 새벽 3시에
연속 지원"은 못 막는다. 루프 버그 하나면 그 일이 벌어지고, 사용자 실명으로 나간
지원서는 되돌릴 수 없다.

모든 지원이 `claim()` 하나를 지나므로 거기서 센다:

```yaml
limits:
  max_per_day: 10   # 하루 누적
  max_per_run: 3    # 실행 1회당 — 루프 버그가 하루치를 한 번에 태우는 걸 막는다
```

상한에 걸리면 `claim()`이 `None`을 돌려준다. 예외를 던지지 않는 이유: 호출부는 이미
"None이면 넘어간다"를 처리하고 있다. 상한을 새 실패 경로로 만들면 처리를 빼먹은
곳에서 프로세스가 죽고, 그건 우아한 실패가 아니다.

```bash
python cli.py quota    # 오늘 몇 건 남았는지
```

## 무엇이 자동화되고 무엇이 LLM 몫인가

원티드 지원 흐름을 실제로 눌러보고 나눈 경계다.

### 코드로 끝나는 것 — LLM 호출 0회

| 단계 | 근거 |
|---|---|
| 공고 수집 | 원티드·자소설은 공개 JSON API, 사람인은 정적 HTML. 전부 결정론적 |
| 하드컷 + 점수 | 순수 문자열 연산. 1157건을 훑는 데 LLM 0회 |
| 지원가능성 판정 | blocker 규칙이 전부 정규식·파일존재·날짜 비교 |
| 중복 판정 | `canonical_key` 정규화 후 완전일치 |
| 폼 채우기 (이름·연락처·학력) | 값이 고정. Playwright 셀렉터로 충분 |
| 제출 확인 | 완료 화면 존재 여부. 정규식 |

**여기에 LLM을 넣으면 안 된다.** 느려지고 비싸지고, 무엇보다 같은 입력에 다른 답이
나와서 "왜 지원했는지"를 재현할 수 없게 된다.

### LLM이 나서야 하는 것

| 단계 | 왜 코드로 안 되는가 |
|---|---|
| **자소서 문항 작성** | 본질적으로 생성 작업. 유일하게 명백한 LLM 영역 |
| **이미지형 공고 판독** | 자소설 공고 상당수가 이미지 한 장. 비전 필요 (`IMAGE_ONLY`) |
| **폼 셀렉터 폴백** | 레시피가 깨졌을 때 화면을 보고 "제출 버튼이 어느 것인지" 판단 |
| **애매한 적합도** | 점수 경계선(70~80점)에서 "이 공고가 정말 맞는지" 최종 판단 |
| **비정형 문항 매핑** | "지원 경로를 선택하세요" 같은 예상 못 한 필드 |

### 사람이 해야 하는 것 — 자동화 대상이 아니다

**로그인.** 이건 실측으로 확정됐다. `지원하기` → `id.wanted.co.kr` →
**OAuth만 제공**(Kakao / Apple / Google / 이메일). 비밀번호를 저장해 자동 로그인하는
경로가 **아예 없다.**

그래서 설계가 이렇게 정해진다:

```
사람이 브라우저 프로필에 한 번 로그인
        ↓
에이전트가 그 프로필을 계속 재사용  (Playwright persistent context)
        ↓
세션이 죽으면 → 멈추고 사람을 부른다.  로그인을 시도하지 않는다.
```

`LOGIN_REQUIRED`는 '고칠 수 있는 blocker'가 아니라 **사람을 호출하는 신호**다.
같은 이유로 최종 제출 버튼도 초기에는 사람 승인을 거치는 편이 안전하다 —
지원은 되돌릴 수 없고, 회사에 남는 건 사용자 본인의 이름이다.

## 실측 결과 (2026-08-15, 원티드)

```
수집 1157건 → 적합 702건 → 자동지원 가능 34건 → 실제 제출 1건 ✅
```

레시피가 없을 때는 702건 전부 `NO_RECIPE`로 막혀 자동지원 가능 0건이었다.
`recipes/wanted.json`을 쓰고 재판정하니 34건이 열렸다. 남은 blocker:

| blocker | 건수 | 해소 방법 |
|---|---|---|
| `SCORE_BELOW_BAR` | 656 | 기준 75점. 조정 가능 |
| `NO_DETAIL` | 628 | `scrape.detail_limit` 상향 (현재 120) |
| `ESSAY_REQUIRED` | 11 | 원티드엔 문항이 없다 — 본문 정규식 오탐으로 보인다. 확인 필요 |
| `DOC_MISSING` | 6 | 서류 준비 후 `available_documents`에 등록 |

### 첫 자동지원 (원장 id=2)

```
이빗 · [인턴] 글로벌 콘텐츠 마케터
0:goto → 1:click(건너뜀) → 2:expect → 3:check → 4:expect → 5:submit
→ "지원이 완료되었습니다!" 확인 → submitted 기록 → 상한 1/10 소진
```

### 실제 폼은 설계 예상과 달랐다

`capture`로 뜯어보고 알게 된 것 — **원티드 지원에는 LLM이 낄 자리가 거의 없다.**

| 예상 | 실제 |
|---|---|
| 이름·연락처를 fill | 계정에서 자동으로 채워짐. fill 스텝 불필요 |
| 이력서 파일 업로드 | 플랫폼에 저장된 이력서를 **고름**. 업로드 없음 |
| 자소서 문항 작성 | **문항 자체가 없음** |

실제 동작은 `이력서 체크 → 제출` 둘뿐이다. 이력서 어셈블러(MD SSOT)는 원티드에는
필요 없다는 뜻이다 — 문서를 만들어 올리는 게 아니라 이미 있는 것을 선택하므로.

두 가지가 레시피를 안정시킨다:

- **셀렉터는 `data-attribute-id`를 쓴다.** 클래스명(`Applying_footer__applyButton__eUQSq`)은
  CSS 모듈 해시라 배포마다 바뀐다 — 레시피가 조용히 깨지는 가장 흔한 원인이다.
- **플랫폼이 공짜 안전장치를 준다.** 이력서를 안 고르면 제출 버튼이 `disabled`다.
  그래서 `:not([disabled])` 확인이 실패하면 애초에 제출이 불가능하다.

> 지원 패널은 공고마다 이미 열려 있기도 하고 버튼을 눌러야 하기도 한다. 그래서
> 클릭 스텝은 `optional`이다. 첫 시도가 `#name`을 못 찾고 멈춰서 알아낸 사실이고,
> 실패 스크린샷이 없었으면 원인을 못 찾았을 것이다.

> 개발 중 `IMAGE_ONLY`가 628건 잡혔는데 **전부 오탐**이었다. 원티드는 공고마다
> 표지 썸네일 `image_url`이 붙는데 그걸 '이미지형 공고'로 오인한 것이다. 판별
> 기준을 `image_path`(어댑터가 본문이 이미지라고 판단해 실제로 받아온 것)로
> 바꿔 해소했다. 진단면(`cli.py blocked`)이 없었으면 못 찾았을 버그다.

## 구조

```
config.yaml              필터 규칙 + 자동지원 기준. 코드 수정 없이 여기만 고친다
cli.py                   cron 진입점. 출력은 항상 JSON
src/autoapply/
  normalize.py           canonical_key — 중복지원 방어선
  db.py                  스키마 + v_actionable / v_blocked 뷰
  agent.py               에이전트 인터페이스 (claim / mark_submitted / blocked_summary)
  pipeline.py            수집 → 두 축 판정 → 저장
  adapters/              wanted · saramin · jasoseol
  screening/
    rules.py             축 1: 적합도 (v1 검증 로직)
    applicability.py     축 2: 지원가능성
```

에이전트 한 사이클:

```python
from src.autoapply import agent

for t in agent.next_targets(limit=5):
    ledger = agent.claim(t["job_id"])   # 선점 — 실패하면 이미 처리된 자리
    if ledger is None:
        continue
    ...실제 지원...
    agent.mark_submitted(ledger, evidence_path=shot)
```

`next_targets`는 점수순이 아니라 **(마감임박 → 점수)** 순으로 낸다.
오늘 밤 닫히는 95점짜리가 상시채용 130점짜리보다 급하다.

## 텔레그램 알림 — 에이전트가 스스로 못 넘는 지점

승인 게이트(v1의 `request_approval` — 지원 직전에 폰으로 물어보고 대기)와는 다르다.
v2는 완전 자동화가 목표라 그 게이트를 기본값으로 넣지 않았다. 대신 **일방향 알림** —
보내고 계속 진행한다. 필요해지면 v1 설계를 그대로 옮겨오면 된다(이미 검증됨).

```bash
python cli.py telegram-setup <봇토큰>   # 최초 1회. @BotFather → /newbot → 봇에게 메시지 한 번 → 토큰
python cli.py notify-login              # 수동 트리거 (쿨다운 적용)
```

`scrape` 끝에서 자동으로 붙는다. 실측(2026-08-15)으로 확정된 이유:
원티드는 지원에 OAuth 로그인이 필요하고 **자동 로그인 경로가 없다.** 그래서
`LOGIN_REQUIRED`는 에이전트가 재시도로 못 넘는 지점이고, 이 알림이 그 지점에서
사람을 부르는 유일한 통로다.

```
🔒 로그인 필요
· wanted: 702건 막힘 — 다시 로그인해 주세요
```

`notify.telegram.cooldown_hours`(기본 6시간)로 도배를 막는다 — cron이 매시간
돌아도 세션이 안 살아나는 한 6시간에 한 번만 온다.

**지금 이 알림은 캐스터가 명시적으로 알려줘야 켜진다** (`--session wanted=0`).
세션 생사를 스스로 확인하는 건 아직 없다 — 아래 Playwright 실행기가 붙을 때
실제 신호(로그인 페이지로 튕김)로 자동 트리거된다.

## 실행기 — dry-run이 기본값

```bash
python cli.py browser-login        # 사람이 한 번 로그인. 세션은 profile/browser/ 에 남는다
python cli.py capture <job_id>     # 폼 DOM을 떠서 JSON + 스크린샷 (아무것도 제출 안 함)
python cli.py apply <job_id>       # dry-run: 다 채우고 제출 직전에 멈춘다
python cli.py apply <job_id> --live  # 실제 제출. 되돌릴 수 없다
```

`--live` 없이는 `submit` 스텝이 **실행되지 않는다.** 나머지는 전부 실제로 한다 —
페이지 열고, 폼 채우고, 파일 올리고, 스크린샷을 남긴다.

이게 검증 방식을 정한다. 셀렉터 JSON을 텔레그램으로 보내 승인받는 건 무의미하다:
사람은 `button.css-1x2y3z`가 맞는 버튼인지 알 수 없다. **다 채워진 폼 스크린샷은
알 수 있다.** 그래서 레시피 승인은 사진으로 받는다.

```
dry-run  0:goto → 1:fill → 2:fill → 3:expect → 4:submit(skipped)   ✓ 스크린샷
live     0:goto → 1:fill → 2:fill → 3:expect → 4:submit → 완료화면 확인 → 원장 기록
셀렉터오류 0:goto → 정지, 이유와 함께. 실패 화면도 스크린샷으로 남는다
```

dry-run은 **선점하지 않는다.** 제출하지 않으니 자리를 잡을 이유가 없고, 잡으면
상한만 태우고 그 자리를 다시 못 건드리게 된다.

### 브라우저를 갈아끼울 수 있게 해뒀다

로그인 세션이 사는 곳이 곧 최대 실패 지점이다. 두 선택지의 트레이드오프가 정반대다:

| | `PlaywrightSession` (현재) | `AsideSession` (미도입) |
|---|---|---|
| 의존성 | 없음 | Aside 데스크톱 앱 + CLI |
| 세션 수명 | **썩는다** — 아무도 그 프로필을 안 씀 | 사람이 매일 쓰니 계속 warm |
| headless cron | 가능 | 앱이 떠 있어야 함 |

`runner/session.py`의 `Session` 프로토콜이 둘을 갈라놓는다. 레시피가 쓰는 어휘
(`fill`/`click`/`upload`/`screenshot`)가 양쪽 같으므로, 세션이 실제로 썩는 게
확인되면 그때 파일 하나 추가로 붙인다. **지금 결정하지 않아도 된다.**

세션 생사 판정은 쿠키가 아니라 **실제로 이동해보고 로그인 페이지로 튕기는지**로
한다(`assert_logged_in`). 만료된 쿠키도 파일에는 남아 있기 때문이다. 폼을 반쯤
채운 뒤 튕기는 경우가 있어 스텝마다 확인한다.
