# autoapply

채용공고 수집 → 판정 → **이력서 조립 → 플랫폼 등록 → 지원 폼 작성**까지 자동으로
간다. 사람은 폰에서 버튼 하나를 누른다.

```bash
python cli.py browser-open                # 상주 브라우저 창을 띄운다 (한 번만)
python cli.py autoapply <job_id>          # 조립 → 등록 → 폼 작성 (dry-run)
python cli.py autoapply <job_id> --live   # 제출. 되돌릴 수 없다
python cli.py cycle-apply                 # 대기열 상위 1건을 준비하고 폰으로 사진 전송
python cli.py revise <job_id> "<지시>"    # 수정 요청을 반영해 다시 만들고 재검토 요청
python cli.py builds                      # 이력서 조립·등록 기록 (왜 미완인지)
python cli.py status                      # 한 줄 요약
python cli.py blocked                     # 왜 막혔는지
python cli.py resumes                     # 플랫폼 이력서 목록 (읽기 전용)
```

## 한 사이클

```
수집·판정        코드        LLM 0회. 4,108건 → 적합 2,785 → 지원가능 133
이력서 조립      LLM 3~4회   작성(sonnet) → 검수(haiku) → 편집기 JSON(sonnet)
플랫폼 등록      코드        사본 만들기 + 간단소개·경력·스킬 교체. 완성도 100%
지원 폼 작성     코드        레시피(JSON). dry-run이 기본값
──────────────────────────────────────────────
검토·제출        사람        폰으로 사진을 받고 [승인 / 폐기 / 수정요청]
```

LLM이 들어가는 곳은 **이력서를 쓰는 구간뿐**이다. 수집·판정·등록·제출은 전부 코드다.
각 호출이 무슨 일을 하는지는 [PORTFOLIO.md](PORTFOLIO.md) §4-4에 표로 있다.

## v1과 무엇이 다른가

v1은 사람이 보는 칸반(`미확인 / 관심 / 작성중 / 지원완료`)이 중심이었다. 무인 운영에는
그 상태기계가 필요 없다. 대신 두 가지를 새로 세웠다.

### 1. 판정 축을 둘로 갈랐다

| 축 | 질문 | 테이블 |
|---|---|---|
| 적합도 | 이 공고가 나한테 맞나 | `screening` (v1 로직 그대로 — 검증됨) |
| 지원가능성 | 이걸 자동으로 지원할 수 있나 | `applicability` (신규) |

둘은 직교한다. 실측에서 132점짜리(러쉬에잇 백엔드)가 `NO_RECIPE` 하나 때문에 막혔고,
반대로 점수는 낮은데 폼이 단순한 공고도 있다. 하나의 점수로 뭉개면 에이전트는
**"왜 지원 안 했는지"를 설명할 수 없다.**

### 2. 중복지원을 DB가 막는다

`apply_ledger.canonical_key`에 UNIQUE를 걸었다. 지원을 *시도하기 전에* 선점 행을
넣으므로, 지원 도중 프로세스가 죽어도 다음 실행이 같은 자리를 다시 건드리지 않는다.

실측에서 바로 값을 했다 — 원티드가 같은 자리(바카티오 `Backend Engineer`)를
`id=280`, `id=281`로 두 번 올려놨고, 2차 선점이 차단됐다.

```
claim(280) → ledger 1     선점 성공
claim(281) → None         같은 자리, 차단됨
```

방어를 코드가 아니라 스키마에 둔 이유: 사람이 안 보는 시스템에서
"죽었다 살아나서 또 지원"은 반드시 일어나고, 그때 사과할 사람이 없다.

### 3. 지원 속도에 상한을 걸었다

UNIQUE 제약은 **"같은 자리에 두 번"만** 막는다. "서로 다른 200개 자리에 새벽 3시에
연속 지원"은 못 막는다. 루프 버그 하나면 그 일이 벌어지고, 사용자 실명으로 나간
지원서는 되돌릴 수 없다.

모든 지원이 `claim()` 하나를 지나므로 거기서 센다:

```yaml
limits:
  max_per_day: 10   # 하루 누적
  max_per_run: 3    # 실행 1회당 — 루프 버그가 하루치를 한 번에 태우는 걸 막는다
```

상한에 걸리면 `claim()`이 `None`을 돌려준다. 예외를 던지지 않는 이유: 호출부는 이미
"None이면 넘어간다"를 처리하고 있다. 상한을 새 실패 경로로 만들면 처리를 빼먹은
곳에서 프로세스가 죽고, 그건 우아한 실패가 아니다.

```bash
python cli.py quota    # 오늘 몇 건 남았는지
```

## 무엇이 자동화되고 무엇이 LLM 몫인가

원티드 지원 흐름을 실제로 눌러보고 나눈 경계다.

### 코드로 끝나는 것 — LLM 호출 0회

| 단계 | 근거 |
|---|---|
| 공고 수집 | 원티드·자소설은 공개 JSON API, 사람인은 정적 HTML. 전부 결정론적 |
| 하드컷 + 점수 | 순수 문자열 연산. 4,108건을 훑는 데 LLM 0회 |
| 지원가능성 판정 | blocker 규칙이 전부 정규식·파일존재·날짜 비교 |
| 중복 판정 | `canonical_key` 정규화 후 완전일치 |
| 편집기·폼 채우기 | 무엇을 쓸지는 이미 JSON에 정해져 있다. 여기는 옮기는 일뿐 |
| 제출 확인 | 완료 화면 존재 여부. 정규식 |

**여기에 LLM을 넣으면 안 된다.** 느려지고 비싸지고, 무엇보다 같은 입력에 다른 답이
나와서 "왜 지원했는지"를 재현할 수 없게 된다.

### LLM이 나서야 하는 것

| 단계 | 왜 코드로 안 되는가 |
|---|---|
| **자소서 문항 작성** | 본질적으로 생성 작업. 유일하게 명백한 LLM 영역 |
| **이미지형 공고 판독** | 자소설 공고 상당수가 이미지 한 장. 비전 필요 (`IMAGE_ONLY`) |
| **폼 셀렉터 폴백** | 레시피가 깨졌을 때 화면을 보고 "제출 버튼이 어느 것인지" 판단 |
| **애매한 적합도** | 점수 경계선(70~80점)에서 "이 공고가 정말 맞는지" 최종 판단 |
| **비정형 문항 매핑** | "지원 경로를 선택하세요" 같은 예상 못 한 필드 |

### 사람이 해야 하는 것 — 자동화 대상이 아니다

**로그인.** 이건 실측으로 확정됐다. `지원하기` → `id.wanted.co.kr` →
**OAuth만 제공**(Kakao / Apple / Google / 이메일). 비밀번호를 저장해 자동 로그인하는
경로가 **아예 없다.**

그래서 설계가 이렇게 정해진다:

```
사람이 브라우저 프로필에 한 번 로그인
        ↓
에이전트가 그 프로필을 계속 재사용  (Playwright persistent context)
        ↓
세션이 죽으면 → 멈추고 사람을 부른다.  로그인을 시도하지 않는다.
```

`LOGIN_REQUIRED`는 '고칠 수 있는 blocker'가 아니라 **사람을 호출하는 신호**다.
같은 이유로 최종 제출 버튼도 초기에는 사람 승인을 거치는 편이 안전하다 —
지원은 되돌릴 수 없고, 회사에 남는 건 사용자 본인의 이름이다.

## 실측 결과 (2026-08-16)

```
수집 4,108건 → 적합 2,785건 → 자동지원 가능 133건 → 대기열 124건 → 제출 2건
     사람인 2,129 · 원티드 1,161 · 자소설 818
```

133과 124가 다른 이유: `v_actionable`이 **폐기·기지원·플랫폼 간 중복**을 한 번 더
걷어낸다. 같은 자리가 여러 플랫폼에 있으면 대표 하나만 큐에 올린다.

**2026-08-16 — 체인이 처음으로 끝까지 닫혔다.** 수집부터 실제 제출까지 사람이 폰에서
버튼 하나만 눌렀다(공고 1025 데이원컴퍼니, `apply_ledger.submitted`, 증적에
'지원이 완료되었습니다'). 이력서 완성도 100%.

적합 판정 2,785건 중 개발 트랙은 467건뿐이고 경영지원/마케팅/영업이 1,972건이다.
**이력서 하나로는 안 된다**는 뜻이고, 아래 트랙별 사본과 §7-1 재해석 규칙이 거기서 나왔다.

주요 blocker:

| blocker | 성격 |
|---|---|
| `SCORE_BELOW_BAR` | 정상. 기준 75점 |
| `NO_DETAIL` | `scrape.detail_limit` 한계. 통과분이 늘면 뒤가 밀린다 |
| `REQUIREMENT_GAP` | 이력서를 조립해보니 필수요건 근거가 없더라 (아래) |
| `EXTERNAL_ATS` | 외부 채용시스템. 구조상 자동화 불가 |

### 어셈블러가 판정의 사각지대를 메운다

적합도 점수는 **공고에 그 키워드가 있는지만** 세고 사용자가 실제로 할 수 있는지와
대조하지 않는다. 실측: 132점 최고점 공고(Java/Spring 백엔드)가 Java 실무·Oracle·ERP
전부 근거 없음이었다.

어셈블러는 공고를 읽으며 그걸 이미 세고 있었다. `resume_builds`에 남기고
`applicability`가 `REQUIREMENT_GAP`으로 읽는다. 한 번 조립해본 공고에만 붙으므로
첫 시도가 알아내고 이후 판정이 그 공고를 목록에서 뺀다.

## 이력서를 사본에서 시작한다

완성도가 몇 주 동안 **71%에서 멈췄다.** 학력이 저장되지 않았고 링크 입력이 타임아웃
났다. 셀렉터를 계속 고쳤지만 이 층은 원래 잘 깨진다.

그러다 알아챈 것: **학력·링크·언어는 공고가 바뀌어도 안 바뀐다.** 매번 채울 이유가 없다.

원티드 이력서 목록의 `···` 메뉴에 **사본 만들기**가 있다. 완성된 템플릿을 복제하면
안 바뀌는 것은 그대로 따라오고, 파이프라인은 바뀌는 것만 건드린다.

```python
COPY_STEPS = ("text", "experience", "dates", "selects", "skills")
# 학력·링크·언어는 의도적으로 없다 — 사본이 들고 온다
```

결과는 완성도 100%, 그리고 **가장 잘 깨지던 코드 경로가 통째로 사라진 것**이다.
`audit()`도 우리가 안 쓴 섹션은 대조하지 않고 "보존됐는지"만 확인한다.

시작점 자체를 트랙별로 가른다(`config.yaml`의 `resumes.copy_from`):

```yaml
by_track:   {dev: 개발자용, pm: AX개발자, presales: 영업, biz: 영업}
by_keyword: {데브옵스: [devops, sre, kubernetes, ...], AX개발자: [llm, rag, mlops, ...]}
```

키워드가 트랙보다 먼저 걸린다 — 같은 dev라도 인프라 공고면 데브옵스 사본에서 시작한다.

제목은 `{회사} {공고} #{DB 카운터}`다. **목록을 읽어 번호를 정하지 않는다** —
목록은 다른 프로세스가 동시에 바꿀 수 있고, 카운터는 그렇지 않다.

### 비개발 공고에는 개발 이력을 다시 써서 낸다

영업 공고에 지원하는데 내용도 스킬도 개발 얘기였다. 작성 가이드 뒤쪽(§7-1)에 규칙을
적어뒀지만 **긴 가이드에 묻힌 규칙은 무시된다.**

그래서 트랙이 비개발일 때만 재해석 규칙을 프롬프트 본문에 직접 주입한다
(`assemble._track_block`). 스킬도 같은 이유로 제한한다 — 원티드 스킬 칸은 고정 사전이라
서술형 문구가 아예 등록되지 않는다. 도구 고유명사만 쓰게 하니 5/5 등록됐다.

### 정리는 우리가 만든 것만 지운다

이력서가 쌓이므로 정리가 필요한데, 여기서 **사람이 만든 이력서 하나를 지웠다.**
선택 조건이 "오래되었거나 개수를 넘은 것"뿐이었고, 그 조건은 *누가 만들었는지를
한 번도 묻지 않는다.*

- `made_resumes`가 소유의 근거다. **만들자마자** 기록한다 — 채우다 실패한 것도
  우리가 치울 물건이기 때문이다
- 나이·개수는 이제 무엇을 지울지가 아니라, **우리 것 중 무엇부터** 지울지를 정한다
- 기록에 없으면 건드리지 않고 `우리 것 아님(건너뜀)`으로 보고한다

안 지워지는 쪽이 잘못 지우는 쪽보다 훨씬 가볍다.

## 브라우저 창은 한 번만 띄운다

작업 중에 창이 계속 튀어나와 화면을 가로챘다. headless는 원티드가 403으로 막고
(`--headless=new`도 CloudFront 403 — 타이밍 문제가 아니라 확인했다), 창 위치를
화면 밖으로 밀면 macOS가 되돌린다.

해법은 창을 **숨기는** 게 아니라 **띄우는 횟수**를 바꾸는 것이었다. CDP 9222로 상주
브라우저 하나를 띄워두고 이후 모든 프로세스가 거기 붙는다. 사람이 한 번 숨기면
새 창이 안 나오니 계속 숨어 있다.

```bash
python cli.py browser-open   # 한 번만. 이후 모든 실행이 이 창에 붙는다
```

붙은 세션은 `close()`에서 창을 닫지 않는다(`pw.stop()`만 한다). 닫으면 다음 실행이
다시 띄우게 되고, 그러면 원점이다. 숨긴 상태로 이력서 14건 조회에 8.8초.

## 구조

```
config.yaml              필터 규칙 + 자동지원 기준. 코드 수정 없이 여기만 고친다
NEXT.md                  작업 큐. 자기개선 루프가 읽는다
cli.py                   진입점. 출력은 항상 JSON
schedule/                launchd — 2시간마다 깨어난다
src/autoapply/
  normalize.py           canonical_key — 중복지원 방어선
  db.py                  스키마 + v_actionable / v_blocked 뷰
  agent.py               claim / mark_submitted / quota — 모든 지원이 지나는 관문
  pipeline.py            수집 → 두 축 판정 → 저장
  health.py              L1 이상 감지 (LLM 0회)
  llm.py                 claude CLI 호출. 하네스를 걷어내 입력 2토큰
  assemble.py            이력서 조립: 작성 → 검수 → 보강 (+ 수정요청 반영)
  vision.py              스크린샷 판독. 플랫폼을 몰라도 되는 검증 층
  render.py              조립 결과 미리보기 이미지. to_pdf는 현재 미사용(주석 참조)
  orchestrator.py        자기개선. 브랜치에서만 움직인다
  adapters/              wanted · saramin · jasoseol
  notify/                telegram — 알림 · 사진 · 폰 명령 수신
  runner/
    session.py           브라우저. Session 프로토콜로 백엔드 교체 가능
    probe.py             세션 생사 확인
    apply.py             레시피 실행. dry-run이 기본값
    resume_editor.py     원티드 이력서 편집기 자동 입력
    capture.py           폼 DOM 캡처 (레시피 작성 근거)
  screening/
    rules.py             축 1: 적합도
    applicability.py     축 2: 지원가능성
```

에이전트 한 사이클:

```python
from src.autoapply import agent

for t in agent.next_targets(limit=5):
    ledger = agent.claim(t["job_id"])   # 선점 — 실패하면 이미 처리된 자리
    if ledger is None:
        continue
    ...실제 지원...
    agent.mark_submitted(ledger, evidence_path=shot)
```

`next_targets`는 점수순이 아니라 **(마감임박 → 점수)** 순으로 낸다.
오늘 밤 닫히는 95점짜리가 상시채용 130점짜리보다 급하다.

## 폰이 검토 창구다

준비된 지원서의 **채워진 폼 스크린샷**이 폰으로 온다. 셀렉터나 로그를 보내는 건
의미가 없다 — 사람은 `button.css-1x2y3z`가 맞는 버튼인지 알 수 없지만 사진은 안다.

```
📄 지원 준비됨
124점 · 인졀미 — 서비스 운영·SW 개발자
[스크린샷]

[승인]  [폐기 — 지원대상에서 제외]  [수정요청]
```

**세 갈래인 이유**: 예/아니오로는 부족했다. 대부분의 "아니오"는 거절이 아니라
수정 요청이다. 수정요청을 누르면 다음에 보내는 자유 텍스트가 지시로 쓰이고,
그걸 반영해 다시 만든 뒤 **같은 세 버튼으로 돌아온다**(`cli.py revise`).
수정 지시가 있으면 72시간 캐시를 우회한다 — 캐시된 결과를 다시 주면 루프가 안 끝난다.

폐기는 `jobs.dropped_at`에 남는다. `applicability`에 쓰지 않는 이유는 그쪽이
재판정(`reevaluate`) 때 덮어써지기 때문이다 — **사람의 결정과 시스템이 다시 계산하는
값은 같은 자리에 두면 안 된다.**

### 수정 요청은 원장에 쌓인다

지시가 한 번 쓰이고 사라지면 같은 공고에 두 번째 요청이 왔을 때 첫 번째를 잊고,
다음 공고에서는 같은 말을 또 해야 한다. 그래서 재작성 **전에** 한 줄로 남긴다
(`profile/revision-log.md`). 이력서를 쓸 때 작성 가이드와 **함께** 읽는다.

```
- 2026-08-16 · #79 코드비전 AI 서비스 풀스택 개발자(개발) — 공고와 무관한 인프라 경험
  제외 요청. 풀스택 개발직이고 자격요건·우대사항 어디에도 인프라 없음
- 2026-08-16 · #79 코드비전 AI 서비스 풀스택 개발자(개발) — 간단 소개를 더 짧게.
  취향 — 공고와 무관
```

**지시만 남기면 안 된다.** "인프라 빼줘"는 그 공고가 프론트엔드였기 때문에 맞는 말이지
언제나 맞는 말이 아니다. 그래서 그때 그게 맞았던 이유를 같이 적고 두 종류로 가른다.

| 근거 | 다음 공고에서 |
|---|---|
| 공고 근거 — **무엇을** 쓸지에 대한 지시 | 같은 근거가 성립할 때만 적용 |
| `취향 — 공고와 무관` — **어떻게** 쓸지 | 공고를 가리지 않고 적용 |

같은 공고에서 받은 지시는 따로 묶어 "전부 지킨다"로 넘긴다. 섞어두면 남의 공고 지시를
이 공고에 적용하거나, 반대로 방금 받은 지시를 흘려보낸다.

원장을 `profile/resume/`가 **아니라** 그 바깥에 두는 이유: `load_guide()`가 그 폴더의
`.md`를 전부 합쳐 사실 저장소로 넘긴다. 안에 두면 "지난번에 이렇게 해달라고 했다"가
"이것이 규칙이다"와 같은 무게로 읽힌다. 옮겨져도 걸러지도록 이름으로 한 번 더 막는다.

반복되는 지적은 원장이 아니라 `resume-guide.md`에 규칙으로 올라가야 한다. 그건 아직
사람이 한다 — 한 공고의 특수한 요구가 규칙이 되면 이후 모든 이력서가 조용히 오염되므로,
자동으로 올리기 전에 물어보는 흐름이 먼저다.

기록한 줄은 폰으로 되돌려준다. 요약이 지시를 잘못 옮기는 경우가 있는데(특히 '짧게'
같은 한 단어), 그 줄은 앞으로 모든 이력서 프롬프트에 실려 나가므로 사람이 바로
알아보고 고칠 수 있어야 한다.

`apply --live`가 아니라 `autoapply --live`인 이유: 전자는 이력서를 다시 채우지 않고
제목으로 고르기만 한다. 미리보기 이력서는 다음 사이클이 덮어쓰므로, 나중에 제출하면
**다른 공고용 이력서가 나간다.** 후자는 제출 직전에 그 공고용으로 다시 채운다.

운영 명령도 폰에서 받는다:

```
/status /quota /blocked /targets /pause /resume /queue
그 외 자유 텍스트 → 개발 지시 큐 (브랜치에서만 작업, main 금지)
```

`/pause`가 실질적으로 쓸모 있다 — 뭔가 이상하면 지원 준비만 멈추고 수집·판정은
계속 돌릴 수 있다.

### 세션이 죽으면 사람을 부른다

원티드는 지원에 OAuth 로그인이 필요하고 **자동 로그인 경로가 없다.** 그래서
`LOGIN_REQUIRED`는 재시도로 못 넘는 지점이고, 알림이 유일한 통로다.

세션 판정은 세 갈래다. **모르는 것과 죽은 것을 구분한다** — 확인 불가를 죽음으로
처리하면 멀쩡한 세션에 대해 사람을 불러대고 판정이 오염된다:

```
로그인 페이지로 튕김        → 죽음 (확정)
로그인 상태에서만 닿는 URL  → 살아있음 (확정)
둘 다 아님                  → 확인 불가
```

URL 리다이렉트를 DOM 셀렉터보다 먼저 본다. 렌더링 타이밍과 무관하게 결정되므로
느린 환경(launchd 콜드스타트)에서도 흔들리지 않는다 — 실제로 셀렉터 방식은
03시 실행에서 멀쩡한 세션을 죽었다고 판정했다.

## 실행기 — dry-run이 기본값

```bash
python cli.py browser-login        # 사람이 한 번 로그인. 세션은 profile/browser/ 에 남는다
python cli.py capture <job_id>     # 폼 DOM을 떠서 JSON + 스크린샷 (아무것도 제출 안 함)
python cli.py autoapply <job_id>   # dry-run: 조립·등록·폼 작성까지, 제출 직전에 멈춘다
python cli.py autoapply <job_id> --live  # 실제 제출. 되돌릴 수 없다
```

`--live` 없이는 `submit` 스텝이 **실행되지 않는다.** 나머지는 전부 실제로 한다 —
페이지 열고, 폼 채우고, 파일 올리고, 스크린샷을 남긴다.

이게 검증 방식을 정한다. 셀렉터 JSON을 텔레그램으로 보내 승인받는 건 무의미하다:
사람은 `button.css-1x2y3z`가 맞는 버튼인지 알 수 없다. **다 채워진 폼 스크린샷은
알 수 있다.** 그래서 레시피 승인은 사진으로 받는다.

```
dry-run   0:goto → 1:click → 2:expect → 3:check → 4:expect → 5:submit(skipped)  ✓ 스크린샷
live      … → 5:submit → 완료화면 확인 → 원장 기록
셀렉터오류 멈춤 + 이유. 실패 화면도 스크린샷으로 남는다
```

dry-run은 **선점하지 않는다.** 제출하지 않으니 자리를 잡을 이유가 없고, 잡으면
상한만 태우고 그 자리를 다시 못 건드리게 된다.

### 브라우저를 갈아끼울 수 있게 해뒀다

로그인 세션이 사는 곳이 곧 최대 실패 지점이다. 두 선택지의 트레이드오프가 정반대다:

| | `PlaywrightSession` (현재) | `AsideSession` (미도입) |
|---|---|---|
| 의존성 | 없음 | Aside 데스크톱 앱 + CLI |
| 세션 수명 | **썩는다** — 아무도 그 프로필을 안 씀 | 사람이 매일 쓰니 계속 warm |
| headless cron | 가능 | 앱이 떠 있어야 함 |

`runner/session.py`의 `Session` 프로토콜이 둘을 갈라놓는다. 레시피가 쓰는 어휘
(`fill`/`click`/`upload`/`screenshot`)가 양쪽 같으므로, 세션이 실제로 썩는 게
확인되면 그때 파일 하나 추가로 붙인다. **지금 결정하지 않아도 된다.**

세션 생사 판정은 쿠키가 아니라 **실제로 이동해보고 로그인 페이지로 튕기는지**로
한다(`assert_logged_in`). 만료된 쿠키도 파일에는 남아 있기 때문이다. 폼을 반쯤
채운 뒤 튕기는 경우가 있어 스텝마다 확인한다.

### 브라우저 자동화에서 반복해 밟은 함정

전부 **"시킨 대로 됐다고 믿었는데 아니었던"** 부류다. 화면에는 정상으로 보인다.

| 증상 | 원인 |
|---|---|
| 값이 화면엔 있는데 새로고침하면 사라짐 | React 제어 입력에 blur/change가 안 나감 → `click → fill → Tab` |
| 회사명·학교명이 잘려서 저장됨 | 자동완성 드롭다운 재렌더 중 타이핑 유실. 확정 후 대조·교정이 본체 |
| 날짜를 골랐는데 되돌아감 | **저장 요청이 아예 안 나감.** 같은 항목의 다른 칸을 건드려야 PATCH가 나간다 |
| 날짜가 엉뚱한 칸에 들어감 | `has-text("YYYY.MM")`은 빈 칸만 잡아 채울 때마다 인덱스가 밀림 |
| 클릭이 15초 타임아웃 | 팝업 뒤 투명 백드롭이 가로챔. 단 submit은 force 금지 |
| 다음 섹션이 안 열림 | 앞 섹션 팝업이 살아있음. Escape·blur로는 안 닫히고 **다른 제목을 클릭**해야 닫힘 |
| 완성도 100%인데 지원에 못 씀 | `작성 완료`를 눌러야 '작성 중'을 벗어난다 |

그래서 모든 입력 뒤에 **넣은 값과 저장된 값을 대조**한다. 그게 없으면 전부
조용히 지나갔을 문제들이다.
