# autoapply 이어서 진행하기

사용자에게 다음에 뭘 할지 **묻지 않는다.** 큐에서 골라 하고, 결과만 보고한다.

## 절차

### 1. 상태 파악 (매번 처음에)

```bash
git -C /Users/yeilpark/auto-apply log --oneline | head -5
cat /Users/yeilpark/auto-apply/NEXT.md
git -C /Users/yeilpark/auto-apply status --porcelain
```

작업 트리가 더러우면 **먼저 그것부터 정리**한다. 검증 안 된 변경 위에 새 작업을
쌓지 않는다.

### 2. 항목 하나 선택

`NEXT.md`의 `## 진행 중` → 없으면 `## 대기`의 맨 위 미완료 항목.
**한 번에 하나만** 한다. 여러 개를 동시에 하면 무엇이 무엇을 깨뜨렸는지 못 가린다.

### 3. 구현

이 저장소의 설계 원칙을 지킨다:

- **정규식·단순 파싱으로 되는 곳에 LLM을 넣지 않는다.** 수집·판정·폼 조작·중복
  차단은 전부 결정론 코드다. LLM은 이력서 작성/검수 두 군데뿐이다.
- **넣은 값과 저장된 값을 대조한다.** 이 프로젝트에서 잡은 버그는 거의 전부
  "시킨 대로 됐다고 믿었는데 아니었던" 경우다. 브라우저 입력은 특히 그렇다 —
  화면에 보여도 새로고침하면 사라지는 일이 흔하다.
- **모르는 것과 실패한 것을 구분한다.** 확인 불가를 실패로 처리하면 멀쩡한
  상태에 대해 사람을 부르게 된다.
- **되돌릴 수 없는 동작은 하지 않는다.** 실제 지원 제출(`--live`)은 절대 실행하지
  않는다. dry-run까지만 한다.

### 4. 검증

각 항목의 `검증:` 줄에 적힌 조건을 **실제로 실행해서** 확인한다.
말로 "됐을 것"이라고 하지 않는다. 브라우저 작업이면 새로고침 후 값을 다시 읽는다.

검증에 실패하면 그 사실을 `NEXT.md`에 적고 다음 항목으로 넘어간다.
같은 것을 세 번 넘게 시도하지 않는다 — 막힌 이유를 적어두는 게 더 쓸모 있다.

### 5. 커밋과 큐 갱신

```bash
git -C /Users/yeilpark/auto-apply add -A
git -C /Users/yeilpark/auto-apply commit -F - <<'EOF'
<무엇을 왜 고쳤는지. 실측 수치가 있으면 넣는다>
EOF
```

커밋 메시지는 **무엇을 했는지가 아니라 왜 그렇게 했는지**를 적는다.
특히 실측으로 알아낸 함정(어떤 셀렉터가 왜 안 먹었는지)은 반드시 남긴다 —
다음에 같은 데서 막힌다.

그 다음 `NEXT.md`에서 해당 항목을 `## 완료`로 옮기거나, 막혔으면 이유를 적는다.
작업 중 새로 발견한 할 일이 있으면 `## 대기`에 추가한다(검증 조건 포함).

### 6. 보고

사용자에게 세 줄 안으로 보고한다: 무엇을 했고, 검증 결과가 무엇이고,
다음 항목이 무엇인지. 다음에 뭘 할지 **묻지 않는다.**

## 하지 않는 것

- 실제 지원 제출
- `main` 브랜치 외 작업 (이 스킬은 main에서 직접 작업한다. 자율 오케스트레이터가
  브랜치를 쓰는 것과 다르다 — 이건 사용자가 지켜보는 세션이다)
- 사용자에게 다음 작업을 묻는 것
- 큐에 없는 일을 임의로 크게 벌이는 것 (작은 발견은 큐에 적어두고 넘어간다)
